# Domain Companion: E2E & UI Testing

This companion provides specialized inspection patterns for end-to-end (E2E), browser automation (Playwright, Cypress, Selenium), UI component testing, and visual regression suites.

---

## 1. Selector Fragility & Anti-Patterns

### Invariant
E2E selectors must target resilient, user-facing semantic attributes (accessible roles, accessible names, test IDs) rather than fragile DOM hierarchy or implementation-dependent CSS class names.

### Critical Failure Modes
1. **Brittle DOM Hierarchy Selectors**:
   Using chained index paths like `page.click("div.container > div:nth-child(2) > span > button")`. Any minor layout change breaks the test without any change in functionality.
2. **Auto-Generated or Obfuscated CSS Classes**:
   Targeting hashed class names generated by CSS modules or CSS-in-JS (e.g. `page.locator(".btn_x9a2b")` or Tailwind utility chains).
3. **Missing Unique Scope**:
   Clicking a generic locator `page.click("button:has-text('Delete')")` on a table with 20 rows, deleting an arbitrary or random entity.

### Anti-Nitpicking Filter
- Reject findings arguing between `data-testid` vs accessibility selectors (`getByRole`) if both are stable and unambiguous.
- Reject requests to rename `data-testid` attributes if they uniquely identify the target element.

## 2. Timing, Synchronization & Flakiness Elimination

### Invariant
Browser tests must synchronize on deterministic state changes (DOM element visibility, network response arrival, animation completion), NEVER on arbitrary sleep delays.

### Critical Failure Modes
1. **Hardcoded Sleeps (`waitForTimeout`, `sleep`)**:
   ```typescript
   // Defect: 1000ms delay causes flakiness on slow CI runners and wastes time on fast local runs
   await page.click("#checkout-btn");
   await page.waitForTimeout(1000); // FRAGILE: Replace with page.waitForURL("/order-confirmation")
   ```
2. **Race Conditions with Animations & Transitions**:
   Clicking a button while a CSS opacity or sliding transition is still animating, causing clicks to hit the background canvas or miss the target.
3. **Unhandled Asynchronous Network Responses**:
   Clicking a submit button and asserting DOM changes before waiting for the corresponding API network request (`page.waitForResponse(...)`) to finish, causing random failures if the network is slightly delayed.

### Anti-Nitpicking Filter
- Reject flagging timeout duration increases (e.g. `timeout: 10000`) if the underlying wait condition is fully event-driven and deterministic.

---

## 3. Network Mocking vs Real Backend Tradeoffs

### Invariant
E2E tests should clearly delineate whether they are validating pure frontend UI flows (with mocked network APIs) or full-stack integration (against real backend servers). Mixing both unpredictably creates non-reproducible test failures.

### Critical Failure Modes
1. **Incomplete Network Route Interception**:
   Stubbing `api/v1/orders` but allowing `api/v1/user` to hit live staging servers, causing tests to fail when staging is down or rate-limited.
2. **Mock Drift in Browser Route Stubs**:
   `page.route('**/api/user', route => route.fulfill({ body: JSON.stringify(mockUser) }))` where `mockUser` has missing fields that the updated frontend component expects, masking UI rendering bugs.

### Anti-Nitpicking Filter
- Reject complaints about mocking external third-party widgets (e.g. Google Maps, Recaptcha, Intercom) in E2E tests; mocking external third parties is standard best practice.
